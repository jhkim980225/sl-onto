# feature: 스키마 편집 — 캔버스별 메타모델 CRUD

설계: [multi-canvas](../superpowers/specs/2026-07-20-multi-canvas-design.md) §3.4 · §8

새 캔버스는 **빈 스키마**로 시작한다. FMEA 골격조차 물려주지 않는다 — 부서가 다르면 램프 타입
분류가 오염이지 자산이 아니다. 대신 **객체타입을 먼저 정의해야 문서 인제스천이 된다.**

## 왜 정의가 강제되는가 — DB 제약
원본 스키마에 이미 이 FK 가 있었다.
```sql
nodes.type TEXT NOT NULL REFERENCES object_types(type_id)
edges.rel  TEXT NOT NULL REFERENCES relation_types(rel_id)
```
캔버스 스코핑 후 `(canvas_id, type) → object_types(canvas_id, type_id)` 가 된다. 즉 **객체타입이
하나도 없는 캔버스에는 노드를 물리적으로 넣을 수 없다.** "경고와 함께 200"은 선택지가 아니었다.

사용자에게 FK 위반 500 을 보여줄 수는 없으므로 `POST /api/ingest`(`route.ts:42`)와
`PUT /api/sources/[file]` 이 파싱 전에 선제 차단한다.
```json
409 { "error": "이 캔버스에는 객체타입이 없습니다. ◈ 스키마에서 먼저 정의하세요", "needsSchema": true }
```
UI 는 `needsSchema` 를 보면 스키마 드로어로 안내한다.

## API
```
POST/PATCH /api/schema/object-types            upsert { type_id, label_ko, color?, icon?, description? }
DELETE     /api/schema/object-types?type_id=   409 { error, nodeCount } — 그 타입 노드가 남아 있으면
POST/PATCH /api/schema/relation-types          upsert { rel_id, label_ko, src_types[], dst_types[] }
DELETE     /api/schema/relation-types?rel_id=  409 { error, edgeCount } — 그 관계 엣지가 남아 있으면
GET        /api/schema                         메타모델 스냅샷 + capabilities
```
- id 형식 강제: 객체타입 `^[a-z][a-z0-9_-]{0,30}$`, 관계타입 `^[A-Z][A-Z0-9_]{0,30}$`.
- 사용 중 타입 삭제는 **선제 검사 후 409**(`db.objectTypeUsage` / `relationTypeUsage`). FK 위반을
  기다렸다 500 을 내는 대신, 남은 개수를 함께 돌려줘 사용자가 무엇을 지워야 할지 알게 한다.
- 인메모리 모드는 편집을 persist 할 곳이 없어 pg 연결 시도 전에 400.
- `relation_types.src_types`/`dst_types` 는 domain/range — 관계 검증·추론이 이 값을 본다.

## 사람이 정의할 것은 객체타입뿐
**관계타입은 자동 등록된다.** `ensureRelTypes()`(`lib/db.ts:280`)가 엣지 삽입 전에 미등록 관계를
`rel_id = label` 로 `INSERT … ON CONFLICT DO NOTHING` 한다. 스프레드시트의 '관계' 컬럼처럼 시드에
없는 관계가 와도 인제스천이 막히지 않는다. 관계타입 편집 UI 는 **라벨·domain/range 를 다듬는 용도**다.

**객체(인스턴스)도 사람 손이 필요 없다.** `resolveOrCreate`(`lib/ingest/normalize.ts:132`)가 통제
어휘 밖 라벨을 `AUTO_*` 로 auto-create 한다(확신도 **0.66** — 통제 어휘 라벨 0.95·동의어 0.82 보다
낮게, 골든 룰 2). 원료 문서에서 새 부품이 500개 쏟아져도 **스키마는 안 건드린다.**

정리하면: 타입(스키마)은 사람이 한 번, 인스턴스는 인제스천이 매번.

## 캐시 갱신 — `reloadMetamodel()`
편집 후 `dropCanvasCache` 로 캐시를 통째로 버리지 **않는다**. 그러면 `readyPromise` 까지 날아가
다음 요청이 full hydrate(`loadAll` + 재인덱스 + 서브타입 백필 + 임베딩 백필)를 탄다 — 메타모델
1필드 갱신에는 과하다. `reloadMetamodel()`(`lib/store.ts:122`)이 `cache().metamodel` 만 다시 읽는다.

TTL 재동기화(`syncFromDb`)는 노드·엣지·소스만 다시 읽으므로 **스키마 편집 뒤에는 이 함수를 명시적으로
불러야 한다** — 각 편집 라우트가 응답 전에 호출한다.

## UI
`components/SchemaPanel.tsx` — 좌측 레일 `◈` 드로어. 객체타입·관계타입 목록 + 추가/삭제.
삭제 409 는 서버가 준 한국어 사유를 그대로 노출한다("이 타입의 노드가 12개 남아 있어…").
타입이 바뀌면 `onChanged` 로 부모가 기능 가용성을 다시 조회한다.

## 한계
- **서브타입·속성정의 편집 API 는 없다.** 설계는 `/api/schema/subtypes`·`/property-defs` 를
  포함했으나 구현된 것은 객체타입·관계타입 둘뿐이다. 서브타입은 여전히 `default` 캔버스 시드값만
  존재한다.
- 타입 id 는 변경할 수 없다(upsert 키). 이름을 바꾸려면 새로 만들고 노드를 옮겨야 하는데 그 경로가 없다.
- 빈 캔버스 사용자는 어떤 타입을 만들어야 하는지 알 방법이 없다 — 문서에서 객체타입 자동 유추는 범위 밖.
