# feature: 큐레이션 — 병합·삭제 실행

> **캔버스 범위:** `withCanvasRoute`로 감싸 `?canvas=<id>` 필수 — 실행은 항상 그 캔버스의
> store 캐시(`removeNode`/`removeEdge`/`mergeNodes`)에만 적용된다.

## 책임
[품질-스캔.md](품질-스캔.md)·[스키마-검증.md](스키마-검증.md)가 "무엇이 문제인지" **찾기만** 한
잡음·위반을 사람이 검토하고 승인을 누른 뒤에만 실행한다 — 노드 삭제, 관계(엣지) 삭제, 노드 병합
세 가지. 이 모듈 자체는 아무것도 스캔하지 않는다. 스캔·실행이 두 라우트로 완전히 나뉘어 있다는
것 자체가 골든 룰의 표현이다: **자동 정리는 없다. 버튼은 사람이 누른다.**

## API: `POST /api/curate`
```
body: { op: "deleteNode", id }
    | { op: "deleteEdge", src, rel, dst }
    | { op: "merge", from, into }
```
| op | 동작 | 실패 |
|---|---|---|
| `deleteNode` | 노드 + 관련 엣지 삭제 | 404 노드 없음 |
| `deleteEdge` | 엣지 하나만 삭제(노드는 유지) | 404 엣지 없음 |
| `merge` | `from` 의 관계를 `into` 로 이관 + `from` 라벨을 `into` 의 "병합됨" 속성으로 보존 + `from` 삭제 | 400 동일 노드/미존재 |

응답은 액션마다 갱신된 `totals: { nodes, edges }`를 함께 돌려줘 실행 즉시 카운트를 반영할 수
있게 한다. `merge`는 이관된 엣지 목록(`moved`)과 병합 후 `into` 객체 전체(`getObject`)도
같이 준다.

> **`op`는 실제 요청 필드명이다.** [architecture.md](../architecture.md) §4 API 표는 이전에
> `{action, ...}`로 적혀 있었으나 `app/api/curate/route.ts`의 body 파싱은 `body.op`를 읽는다
> (`action` 필드는 코드 어디에도 없다) — 이 문서 작성 중 발견해 표를 `{op, ...}`로 정정했다.

## 원본 보존 — 병합은 흔적을 남기고 지운다
`merge`는 `from`이 갖고 있던 관계(아웃/인 엣지)를 `into`로 옮기고(중복·자기루프 제거), `from`의
원래 라벨을 `into`의 `속성["병합됨"] = "라벨 (id)"`로 남긴 **다음** `from` 노드 자체는 삭제한다
(`lib/store.ts:411-413`). 즉 노드는 사라지지만 "무엇이 무엇으로 흡수됐는지"는 `into`의 속성에
남는다 — 완전 소거가 아니라 원본 흔적을 보존한 삭제라는 점이 골든 룰 3(원본 보존)의 적용이다.

## 호출자 — 스캔 결과를 그대로 실행 버튼에 매핑
- **품질 스캔** (`components/QualityPanel.tsx`): `dup-candidate`는 "병합 → 대상 라벨" 버튼
  (`merge`), `rel-domain`(스키마 위반)은 "관계 삭제" 버튼(`deleteEdge`), 그 외 전 항목은
  "삭제" 버튼(`deleteNode`). 컴포넌트는 `/api/curate`를 직접 fetch하지 않고 `Workbench.tsx`가
  넘긴 콜백을 호출 — 실제 fetch·재스캔(`refreshQuality()`)은 `Workbench` 쪽 책임이다.
- 실행 후에는 스캔 쪽(`GET /api/quality`)을 다시 불러 배지 카운트를 갱신한다. 큐레이션
  라우트 자체는 재스캔을 트리거하지 않는다 — "지금 뭐가 남았는지"는 호출자가 다시 물어야 안다.

## 골든 룰 적용
- **실행은 사람 승인 후에만**: 스캔(`lib/quality.ts`/`lib/schema/validate.ts`)은 순수 함수라
  호출해도 아무것도 바뀌지 않는다. 데이터가 바뀌는 유일한 경로가 이 라우트이고, 이 라우트는
  UI 버튼 클릭이 아니면 호출되지 않는다.
- **원본 보존**: 위 "병합은 흔적을 남기고 지운다" 참조.
- **근거 우선**: 큐레이션 자체는 근거를 요구하지 않는다(삭제·병합 대상은 이미 스캔이 근거와
  함께 제시했으므로) — 이 라우트 층위에서 근거를 재검증하지는 않는다.

## 한계
- 큐레이션은 인메모리/DB 캐시에 직접 쓴다 — 실행 취소(undo) 없음. 잘못 삭제·병합하면 원본
  문서를 재업로드하거나(삭제) 되돌릴 방법이 없다(병합, `from`의 관계 이관은 역방향 연산 없음).
  삭제된 노드 자체가 사라지므로 "병합됨" 속성만으로 원상복구는 불가능하다.
- 배치 실행(여러 건 한 번에)이 없다 — 패널 항목마다 버튼 클릭 1회.
