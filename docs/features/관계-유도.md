# feature: 관계 유도 — 온톨로지가 스스로 찾은 관계

## 책임
현재 캔버스의 온톨로지 전체(노드+엣지)를 Python 사이드카 `POST /reason`에 보내, 기존 엣지
조합으로 사이드카가 스스로 유도한 관계를 받아온다. `lib/reason.ts`(28줄)는 페이로드 조립과
호출만 하는 얇은 래퍼고, 유도 규칙(전이·대칭·전파 판단) 자체는 pyservice 쪽 로직이다.

```ts
deriveRelations(): Promise<DerivedEdge[]>
// DerivedEdge = { src, rel, dst, rule, via: string[], confidence: number(0..1) }
// rule: "consists-transitive" | "similar-symmetric" | "failure-propagation"
```
`via`는 유도 근거가 된 원본 엣지 체인을 `"A→REL→B"` 문자열 배열로 담는다 — 유도 결과가
어디서 왔는지 추적 가능하게 한다(골든 룰 1, 근거 우선의 연장).

## 골든 룰 원본 보존 — 병합하지 않는다
유도된 엣지는 **store에 병합되지 않는다.** 사이드카가 매 조회마다 다시 계산해 주는 **조회 전용
overlay**다. 원본 온톨로지(DB의 `nodes`/`edges`)는 유도 결과로 절대 오염되지 않는다 — 확정
관계와 "그럴듯하게 유도된" 관계를 같은 테이블에 섞으면 나중에 어느 게 사람이 근거로 넣은
것이고 어느 게 기계가 추측한 것인지 구분할 수 없어진다.

## 장애 격리 — throw 금지
`pyEnabled()`가 `false`(`PYSERVICE_URL` 미설정)면 페이로드 조립조차 생략하고 즉시 빈 배열을
반환한다. 사이드카가 켜져 있어도 네트워크 오류·타임아웃(10s, `lib/pyservice.ts` `pyPost`
공용 클라이언트)이면 마찬가지로 빈 배열이다. **어떤 경로로도 예외를 던지지 않는다** — 사이드카가
죽어 있어도 `GET /api/reason`은 200과 `items: []`를 주지, 500이나 조회 실패로 이어지지 않는다.

## API: `GET /api/reason`
`app/api/reason/route.ts`는 `memoizeByGraphSize`(`lib/graph-memo.ts`)로 결과를 캐싱한다 —
사이드카 추론이 O(전체 그래프)라 매 요청 재계산 대신 그래프 크기가 바뀔 때만 다시 부른다.
응답 `{ items: DerivedEdge[], scannedAt }`.

## UI: `components/ReasonPanel.tsx` · `components/useReason.ts`
- `useReason(ontologyBuilt)` 훅이 온톨로지 구축 완료 후 자동으로 `GET /api/reason`을 부르고,
  상태(`loading`/`error`/`derivedRelations`)를 관리한다. 사이드카 오류도 `[]`로 오므로
  패널은 "유도된 관계가 없습니다"로 조용히 표시된다.
- **확신도는 항상 노출**(골든 룰 2) — `ConfidenceBar`가 `confidence`를 퍼센트 바로 그린다.
  유도 근거 체인은 `ContradictionsPanel`과 같은 `nodeIndex`/`buildChains`/`TraceNode` 헬퍼를
  재사용해 렌더한다 — 확정 관계 화면과 시각적으로 다른 색(`#00a2e5` 유도 전용 톤)을 써서
  "이건 사람이 확인한 관계가 아니다"를 구분한다.

## 확장 이음새
- 유도 규칙 추가·변경은 사이드카(`pyservice`) 쪽 몫이다. `lib/reason.ts`는 `DerivedRule` 유니온만
  넓히면 새 규칙 레이블을 받을 수 있다.
- 유도 결과를 사람이 검토 후 확정 엣지로 승격하는 흐름은 아직 없다 — 지금은 조회·시각화까지만.
