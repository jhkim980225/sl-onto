# feature: 벡터 임베딩

> **캔버스 범위:** 임베딩은 노드 텍스트를 벡터로 바꾸는 상태 없는 함수라 그 자체엔 캔버스가 없다.
> 다만 결과가 앉는 `nodes.embedding` 컬럼과 백필 대상 조회는 전부 `canvas_id` 조건이 붙는다(아래 §캔버스 스코프).
>
> **모델 교체(코드 완료·배포 대기):** 브랜치 `feat/document-chunking` 에서 `multilingual-e5-base`
> (768dim, 512토큰)로 상향했다. `lib/embed.ts` 진입점이 `embedQuery`(`query: ` 접두어)·
> `embedPassage`(`passage: `)로 갈렸다 — e5 계열은 접두어를 요구한다. 아래 384/MiniLM 서술은
> **현재 운영(v79)** 기준이며, 배포 후 갱신한다.

## 책임
질의·노드 텍스트를 384차원 벡터로 바꾼다. `lib/embed.ts`(43줄)는 상태를 갖지 않는 순수 래퍼로,
실제 연산은 Python 사이드카 pyservice의 `POST /embed`가 한다. 모델은
`sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`(384-dim, `max_seq_length=128`토큰 ≈
한국어 250~350자, [document-chunking 설계](../superpowers/specs/2026-07-20-document-chunking-design.md)
실측)다. 노드 임베딩 대상 텍스트는 `lib/db.ts:229` `embedText(label, props)` = `라벨 + "\n" + 속성값
join(" ")`(키·타입·서브타입은 버림) — 라벨 위주라 128토큰 한계가 아직 문제되지 않는다.

## 모듈: `lib/embed.ts` · `lib/pyservice.ts`
```ts
embedEnabled(): boolean                          // = pyEnabled() = !!PYSERVICE_URL
embed(texts: string[]): Promise<number[][]>      // 빈 입력·미가용이면 []
embedOne(text: string): Promise<number[] | null> // 단건 편의
backfillEmbeddings(): Promise<{ embedded: number; skipped: boolean }>
```
`lib/pyservice.ts`(36줄)의 `pyPost()`가 모든 사이드카 태스크(embed·llm·parse·reason)가 공유하는
공용 HTTP 클라이언트다. **어떤 네트워크 오류·타임아웃(10s)·HTTP 오류도 삼켜서 `null`을 반환한다
(throw 금지)** — 실패는 `console.warn`으로만 남는다.

## 장애 격리 — 사이드카가 죽어도 검색은 산다
`embedEnabled()`가 `false`(`PYSERVICE_URL` 미설정)거나 사이드카가 응답하지 않으면 `embed()`는
조용히 빈 배열을 준다. 이를 소비하는 [자연어-검색.md](자연어-검색.md)의 후보 확장은 빈 결과를
규칙기반 폴백으로 흡수하므로, **임베딩이 완전히 꺼진 상태에서도 검색 자체는 계속 동작한다.**
임베딩은 "있으면 더 좋은" 후보 확장 계층이지 검색의 필수 경로가 아니다.

## 백필: `backfillEmbeddings()` — 멱등
`nodes.embedding IS NULL`인 노드만 64개씩 배치로 채운다(`BATCH=64`). 이미 채워진 노드는 절대
건드리지 않으므로 몇 번을 다시 불러도 결과가 같다(멱등). DB(`dbEnabled()`)나 사이드카
(`embedEnabled()`) 중 하나라도 미가용이면 즉시 `{embedded: 0, skipped: true}`로 skip — 예외를
던지지 않는다. 배치 도중 사이드카가 끊겨 반환 벡터 수가 배치 크기와 다르면 그 지점에서 멈추고
나머지는 다음 호출에 맡긴다(NULL로 남아 있으므로 재실행이 안전하게 이어받는다).

## 트리거 — 세 경로 모두 비차단
| 시점 | 코드 | 비고 |
|---|---|---|
| 부팅(hydrate 완료 후) | `lib/store.ts:258` `scheduleEmbedBackfill(canvasId)` | 캔버스 적재 직후 자동 |
| 문서 병합 후(신규 노드 있을 때) | `lib/store.ts:304` (`mergeDelta` 안) | 새 노드가 벡터 검색에도 보이게 |
| 수동 재트리거 | `POST /api/admin/embed-backfill` | `app/api/admin/embed-backfill/route.ts` — 인증 없음(ponytail, 1차 MVP) |

세 경로 모두 백그라운드로 돈다(`void ...then().catch(() => {}).finally(...)`) — 요청·부팅을
막지 않는다. `lib/store.ts:23-48`의 `backfillRunning`(단일 실행 게이트)과
`backfillPending`(대기 중인 캔버스 id `Set`)이 동시 실행을 1개로 제한하면서도, A 캔버스가
백필 중 B 캔버스가 요청하면 A 완료 후 B를 재실행하도록 캔버스별로 큐잉한다(불린 하나였을 때는
어느 캔버스가 대기 중인지 잃어버려 B의 노드가 영원히 `NULL`로 남는 버그가 있었다).
백그라운드 태스크는 요청의 `AsyncLocalStorage` 캔버스 컨텍스트 밖에서 돌기 때문에
`withCanvas(canvasId, () => backfillEmbeddings())`로 컨텍스트를 다시 씌운다.

## 캔버스 스코프
`nodes.embedding` 컬럼 자체는 캔버스 구분 없이 모든 행에 존재한다(`vector(384)`,
`lib/db/schema.sql:77`). 격리는 컬럼이 아니라 **쿼리 조건**에서 일어난다 — `nodesMissingEmbedding()`·
`setEmbedding()`·`semanticSearch()`(`lib/db.ts:432-477`) 전부 `WHERE canvas_id = $n`을 건다.
백필도 벡터 후보도 현재 캔버스 밖으로 새거나 섞이지 않는다.
