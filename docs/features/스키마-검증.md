# feature: 스키마 검증 — 형식 온톨로지 위반 보고(차단 없음)

> **캔버스 범위:** 기본 인자가 `allNodes()`/`allEdges()`/`getMetamodel()`(현재 캔버스 캐시)라
> [다중-캔버스.md](다중-캔버스.md)의 캔버스별 격리를 그대로 물려받는다. 테스트는 이 기본값을
> 안 쓰고 합성 `(nodes, edges, metamodel)`을 직접 주입한다(아래 "테스트" 참조).

## 책임
`lib/schema/validate.ts`의 `scanSchemaViolations()`가 실데이터를 **메타모델**(캔버스별
`relation_types` domain/range · `object_subtypes` · `property_defs` — [스키마-편집.md](스키마-편집.md))
과 대조해 어긋난 곳을 `QualityIssue`로 **보고만** 한다. 인제스천을 막지 않고, 이미 들어온
노드·엣지를 지우거나 고치지도 않는다 — "위반은 경고+큐레이션, 차단 없음"이라는 설계 결정
그대로다([2026-07-09-formal-ontology-schema-design.md](../superpowers/specs/2026-07-09-formal-ontology-schema-design.md)
§B "검증 엔진"). 실행(삭제·관계삭제)이 필요하면 사람이 [큐레이션.md](큐레이션.md)
(`POST /api/curate`)을 눌러야 한다 — 이 모듈 자체는 아무것도 쓰지 않는 순수 함수다.

## 왜 차단하지 않는가
스펙의 정책 결정(확정)은 "위반은 경고+큐레이션(차단 없음)"이다. `POST /api/ingest`가 이미
빈 스키마 캔버스는 409로 선제 차단하고 있는데([스키마-편집.md](스키마-편집.md)), 그 위에 개별
행 단위로 또 차단을 걸면 실무 문서(오탈자·구형 표기·범위 밖 값이 섞인)가 대량으로 인제스천
실패한다. 대신 **일단 받아들이고 사후에 목록으로 보여줘 사람이 판단**하게 한다 — 골든 룰
2(확신도 항상 노출, 최종 판단은 엔지니어)의 스키마 버전이다.

## 규칙 4종
| kind | 판정 | confidence |
|---|---|---|
| `rel-domain` | 엣지 src/dst 타입이 그 관계의 `src_types`/`dst_types` 밖(둘 다 빈 배열이면 무제약이라 스킵 — 자동 등록 관계는 제약이 항상 빈 배열이라 자연히 스킵) | 85 |
| `bad-subtype` | 노드 `st` 값이 `(type_id, st_id)` 조합으로 `object_subtypes`에 없음 | 80 |
| `missing-prop` | `property_defs`에 `required=true`로 정의된 속성이 그 타입 노드에 없음(1차 시드는 전부 `required=false`라 실데이터 0건) | 60 |
| `bad-datatype` | 정의된 속성 값이 `datatype`과 불일치 — `number`는 `parseFloat` 실패 기준("3 EA"처럼 선행 숫자가 있으면 통과), `enum`은 `options` 밖, `text`는 항상 통과 | 70 |

`doc` 노드는 네 규칙 전부에서 제외된다(`objNodes = nodes.filter(n => n.type !== "doc")`,
`lib/schema/validate.ts:28`). 근거 문서(파일명 최대 2개)는 `evidenceOf(nodeId)`에서 채운다 —
합성 주입 노드는 store에 없어 evidence가 자연히 빈 배열이 된다(테스트가 허용하는 상태).
[품질-스캔.md](품질-스캔.md)와 같은 관례로 규칙당 상한 8건.

## `lib/quality.ts`에 합류 — 같은 스캔·같은 실행 경로
`scanQuality()`(`lib/quality.ts:188`)는
`[...scanDupCandidates(), ...scanOrphans(), ...scanNoEvidence(), ...scanSchemaViolations()]`로
[품질-스캔.md](품질-스캔.md)의 3종(중복 후보·고립·근거없음)과 이 4종을 **한 배열**에 합쳐
`GET /api/quality`로 내보낸다. 즉 스키마 검증은 별도 엔드포인트·별도 패널이 아니라 기존 품질
스캔 배지("🧹 정리 N건") 카운트에 그대로 더해진다. `components/QualityPanel.tsx`는
`QualityKind` 7종 전부에 아이콘·라벨·색을 매핑해 구분한다 — 기존 3종(잡음 정리)은 앰버,
스키마 위반 4종은 레드. `rel-domain`은 `edge` 필드가 채워져 있어 패널이 "관계 삭제" 버튼
(`deleteEdge`)을 보여주고, 나머지는 공통 "삭제" 버튼(`deleteNode`)을 쓴다.

## 서브타입 분류 — `lib/schema/classify.ts`와의 관계
`classifyNode()`/`classifyMissing()`은 라벨·요약·속성 값 텍스트에 서브타입 `keywords`를
매칭해 `st`가 없는 노드에 서브타입을 **자동으로 채워주는** 별개 기능이다(결정론적 키워드
히트 수 최대, LLM 아님). `bad-subtype` 규칙과는 방향이 반대다 — `classify`는 "미분류를
채운다", `validate`는 "잘못 분류된 것을 찾는다". `st`가 아예 없는 노드는 미분류 상태일 뿐
`bad-subtype` 위반이 아니다(위반은 `st`가 있는데 그 값이 정의 밖일 때만).

## 왜 인자 기본값이 store 스냅샷인가 — 그리고 테스트는 왜 다르게 하는가
```ts
export function scanSchemaViolations(
  nodes: Node[] = allNodes(),
  edges: Edge[] = allEdges(),
  metamodel: Metamodel = getMetamodel()
): QualityIssue[]
```
운영 경로(`scanQuality()`)는 인자 없이 호출해 현재 캔버스 store를 그대로 스캔한다. 반면
`lib/schema/validate.test.ts`는 실제 시드 데이터에 의존하지 않도록 합성
`(nodes, edges, metamodel)`을 매 테스트마다 직접 만들어 주입한다 — 규칙별 동작(제약 위반 1건
검출, 무제약/미등록 관계 스킵, 정의 밖 서브타입만 검출, `doc` 노드 제외, 규칙당 상한 8건 등)을
실 데이터 변동과 분리해 고정한다.

## 골든 룰 적용
- **확신도 항상 노출**: 4종 모두 규칙별 고정 confidence(85/80/60/70) — 애매함이 없는 구조적
  위반이라 [품질-스캔.md](품질-스캔.md)의 "검토" 톤(45%)보다 전반적으로 높게 잡혀 있다.
- **근거 우선**: `ev()` 헬퍼가 항상 근거 문서를 채우려 시도한다(합성 노드만 예외).
- **원본 보존 + 차단 없음**: 위반이 있어도 노드·엣지·속성 원본 값을 건드리지 않는다. 고치는
  것은 사람이 [큐레이션.md](큐레이션.md)으로 지우거나, [스키마-편집.md](스키마-편집.md)로
  메타모델(허용 범위) 쪽을 넓히거나 둘 중 하나를 선택할 문제다 — 이 모듈은 그 선택을 강제하지
  않는다.

합성 주입 노드의 `evidence` 빈 배열 허용을 합성 메타모델로 고정 검증.
