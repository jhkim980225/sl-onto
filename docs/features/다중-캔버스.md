# feature: 다중 캔버스 — 도메인별 워크스페이스

설계: [multi-canvas](../superpowers/specs/2026-07-20-multi-canvas-design.md)

캔버스 = 부서/제품군 하나가 쓰는 **완전 격리** 워크스페이스. 새 캔버스는 데이터도 스키마도 0에서
시작한다 — 램프 지식이 한 건도 새어 들어가지 않고, 새 캔버스 문서가 램프 쪽을 오염시키지도 않는다.
부트스트랩 `default`(램프) 캔버스만 예외로 FMEA 메타모델이 시드된다.

현재 `default` 캔버스: **180 노드 / 2,199 엣지 / 41 문서**. 운영 배포 v79.

## 요청 경로
```
클라이언트  lib/api-client.ts  apiFetch() → 모든 URL 에 ?canvas=<id> 부착
   ▼
Route Handler  withCanvasRoute(req, handler)      lib/canvas-route.ts:10
   ├─ ?canvas 누락 → 400 (기본 캔버스로 조용히 폴백하지 않는다 — 남의 부서 데이터를 보여주게 된다)
   ├─ 없는/삭제된 캔버스 → 404
   └─ withCanvas(id, handler)                     lib/canvas-context.ts:13  (AsyncLocalStorage)
        ▼
      lib/store.ts:96  cache() → CACHES.get(currentCanvas())
        ▼
      lib/db.ts        모든 쿼리에 canvas_id 조건
```
`app/api/**/route.ts` 29개 중 **26개가 `withCanvasRoute` 로 감싸져 있다**. 나머지 3개
(`/api/canvases`, `/api/canvases/[id]`, `/api/canvases/[id]/restore`)는 캔버스 자체를 다루므로
캔버스 컨텍스트가 없다.

## 왜 AsyncLocalStorage 인가
store 호출이 **39파일 276곳**이다. 함수마다 `canvasId` 인자를 추가하면 기계적이지만 리뷰 불가능한
크기가 되고 그 안에 실수가 섞인다. ALS 는 라우트 진입점 한 줄 + store 내부 `cache()` 한 줄로 끝나며
**공개 시그니처가 하나도 안 바뀐다**. `node:async_hooks` 는 표준 라이브러리라 `lib/` 의 프레임워크
비의존 규칙도 지켜진다.

컨텍스트 밖 호출은 기본 캔버스로 폴백하되 개발 모드에서 스택과 함께 경고한다
(`lib/canvas-context.ts:22`) — 테스트·모듈로드용 폴백이지 라우트에서 일어나면 버그다.
백그라운드 임베딩 백필은 요청 컨텍스트 밖에서 돌므로 `withCanvas(canvasId, …)` 로 다시 깐다
(`lib/store.ts:35`).

## 복합 PK 승격
완전 격리이므로 캔버스 A와 B가 **같은 노드 id 를 가질 수 있다**(둘 다 `ILENS` 를 만들 수 있다).
기존 `nodes` PK 는 `id` 단독이라 그대로 두면 충돌한다.

| 테이블 | PK |
|---|---|
| `nodes` | `(canvas_id, id)` |
| `edges` | `(canvas_id, src, rel, dst)` |
| `sources` | `(canvas_id, file)` |
| `object_types` / `relation_types` | `(canvas_id, type_id)` / `(canvas_id, rel_id)` |
| `object_subtypes` / `property_defs` | `+ canvas_id` |
| `meta` / `change_log` / `ai_opinions` | `+ canvas_id` (다른 캔버스 LLM 답변이 캐시로 새면 안 된다) |

## 마이그레이션 — `lib/db/migrations/001-canvas.sql`
`doReady()` 가 `canvases` 테이블 부재를 감지하면 **단일 트랜잭션**으로 1회 실행. 기존 행은 전부
`'default'` 로 귀속만 하고 값은 건드리지 않는다(골든 룰 3). 재실행 시 즉시 반환(멱등).

**단방향이다.** 되돌리기 스크립트가 없고 회수 경로는 DB 백업뿐. `DROP CONSTRAINT` 에 `IF EXISTS`
를 쓰지 않은 것도 의도적 — 제약 이름이 다르면 조용히 넘어가지 말고 트랜잭션째 실패해야 한다.

## 삭제 — 소프트 삭제(휴지통) 강제
`DELETE /api/canvases/[id]` 는 `deleted_at` 만 찍는다. `?purge=1` 영구 삭제는 **휴지통에 있는
캔버스만** 받는다(`lib/canvases.ts:109`). 앱에 인증이 없어서 이 가드가 없으면
`curl -X DELETE '.../api/canvases/default?purge=1'` 한 줄로 운영 온톨로지 전체가 날아간다 —
브라우저의 이름 타이핑 확인은 UI 밖에서 무력하다. 마지막 활성 캔버스는 삭제 불가(409).

## UI
- `components/CanvasPanel.tsx` — 좌측 레일 `▤` 드로어. 목록·전환·생성·이름변경·삭제·휴지통.
- 캔버스 전환 = **소프트 리셋**. 기존 리마운트 리셋(`resetKey`)을 재사용해 `key={canvasId}` 로
  갈아끼운다 — 부분 갱신은 다른 캔버스 잔상이 남을 위험이 있고 신규 코드도 늘어난다.
- 선택 캔버스는 `localStorage` 보존. 삭제된 캔버스를 가리키면 첫 캔버스로 폴백.

## 한계
- **인메모리 모드(`DATABASE_URL` 없음)에서는 캔버스가 `default` 하나뿐이다.** 생성·수정은
  `CanvasWriteUnavailable` → **503**(`lib/canvas-write.ts`). 500 으로 죽지 않게만 처리한 것.
- 캔버스 존재 여부는 인메모리 `Set` 캐시(`lib/canvases.ts:23`) — **단일 파드 전제**. 멀티 레플리카가
  되면 짧은 TTL 로 바꿔야 한다.
- 캔버스 캐시는 전량 상주(`lib/store.ts:111`). 캔버스 수백 개 규모가 되면 LRU 축출 필요.
- 권한·소유자 개념 없음(로그인 없음). 캔버스 간 노드·문서 이동 없음.
- 스펙이 말한 `grep -L withCanvasRoute` 누락 탐지는 **믿을 수 없다** — 캔버스 관리 라우트 3개가
  주석에 그 이름을 적어두어 매칭된다. 실제로는 `import` 여부를 봐야 한다.
