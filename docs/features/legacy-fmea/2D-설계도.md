# feature: 2D 설계도 (도면 입력)

> **레거시 — FMEA 전용.** 이 기능은 동작하지만 신규 투자 대상이 아니다.
> 램프 도면 형상·설계 조건·추론 결과에 종속돼 `default`(램프) 캔버스 밖에서는 의미가 없다.
> **단 `lib/capabilities.ts` 의 409 게이트는 걸려 있지 않다** — 다른 캔버스에서 호출해도 막히지 않고
> 빈 결과가 난다(게이트가 걸린 라우트는 `/infer` `/fmea-draft` `/contradictions` `/bom-check` `/condensation` 5개뿐).
> 제품의 현재 방향은 [../../README.md](../../README.md) 참조.

## 책임
**"차명이 아니라 형상 유사도"**: DXF 도면에서 형상 특징(벤트·실링·개스킷·커넥터·하우징·렌즈)을
추출하고, 과거 프로젝트의 형상 특징과 **가중 일치율**로 비교해 일치/불일치 근거를 함께 반환한다.
차종이 다른 두 모듈이라도 형상이 닮았으면 상위로 랭크되고, 그 유사 프로젝트의 고장 이력을 붙여
보여준다. 판정은 규칙 기반이라 결정론적이고 설명 가능하다.

## 모듈
- `lib/shape-sim.ts`(129줄) — 형상 특징 모델(`ShapeFeatures`) + 가중 유사도 계산(`shapeSimilarity`)
- `lib/drawing-input.ts`(85줄) — 형상 랭킹 → `SIMILAR` 엣지 병합 → 고장 이력 조회 → 설계 조건 후보 조립
- `lib/drawing-risk.ts`(92줄) — 도면 자체 데이터만으로 하는 설계 취약점 규칙 검사
- `components/DrawingPanel.tsx` — 우측 패널 UI(추출 요약·취약점·유사 설계 카드·조건 적용 버튼)
- `app/api/drawing-input/route.ts`(POST) · `app/api/drawing-svg/route.ts`(GET) · `app/api/design-options/route.ts`(GET)

## 형상 유사도 (`lib/shape-sim.ts`)
`featuresFromProps()`가 노드 props 의 `형상.*` 키(하우징·벤트 홀·실링·개스킷 소재·커넥터·렌즈)를
`ShapeFeatures`로 복원하고, `shapeSimilarity(a, b)`가 **특징별 가중치**로 일치율을 낸다.

| 특징 | 가중치 | 비교 방식 |
|---|---|---|
| 벤트(개수+배치) | 0.25 | 개수 동일 1.0 / 차이 1개 0.4, 배치는 문자열 비교와 가중합(0.6:0.4) |
| 실링 | 0.20 | 문자열 비교 |
| 하우징 | 0.20 | 문자열 비교 |
| 커넥터(IP등급) | 0.15 | IP 숫자부 동일 1.0 / 1등급 차이(IP66↔IP67) 0.5 |
| 개스킷 소재 | 0.10 | 문자열 비교 |
| 렌즈 | 0.10 | 문자열 비교 |

문자열 비교(`strSim`)는 완전 일치 1.0, 한쪽이 다른쪽을 포함(예: "밀폐형" ⊂ "밀폐형 슬림") 0.5, 그 외 0.
양쪽 다 값이 있는 특징만 비교 대상에 넣고(비교 불가 특징은 스킵), 최종 점수는 **비교 가능한 특징의
가중치 합으로 정규화**한다. `matched`/`differed` 배열에 사람이 읽는 근거 문구(예: `"벤트 홀 2개(상·하)
일치"`, `"커넥터 등급 상이 (IP67 ↔ IP66)"`)가 함께 담긴다.

`rankSimilarByShape(target, candidates, topN=4)`는 후보 중 형상 특징이 하나도 없는 노드와 자기 자신을
빼고, 점수 내림차순 상위 N개를 반환한다.

## 도면 → 조건 조립 (`lib/drawing-input.ts`)
`analyzeDrawing(parsedProj, drawing)`이 하는 일:
1. 새로 파싱한 프로젝트 노드의 형상 특징 확정(병합 후 store 의 기존 노드 우선, 없으면 파싱본).
2. `proj` 타입 후보 전체(자기 자신 제외) 대상으로 `rankSimilarByShape`(top 4) → 점수 0.3 초과인
   쌍만 `SIMILAR(weight=score)` 엣지로 만들어 `mergeDelta`로 온톨로지에 합류(`infer`의 `seedProject`
   탐색이 그대로 소비).
3. 유사 프로젝트별 `OCCURRED_IN` 고장 이력을 `histOf()`로 뽑는다 — 큐레이션(비-`AUTO_`) 우선 +
   결로/습기/부식 계열 최우선, 중복 제거 후 상위 3건.
4. 도면 자체(제목블록 부품명 + 형상 특징 문구 + 시드 프로젝트)로 `DesignInput` 조건 후보를 조립.

## 설계 취약점 검사 (`lib/drawing-risk.ts`)
`assessDrawing(drawing, ents, market?)`은 도면이 실제로 담은 데이터만으로 4가지 규칙을 판정한다.

| 규칙 | 판정 근거 | level |
|---|---|---|
| 하우징-개스킷 열팽창 차이 | CTE 차이 ≥80 µm/m·K(`CTE`/`cteOf` — `lib/bom-consistency.ts`도 재사용) | 주의 |
| 벤트 홀-발열원 근접 | 도면 텍스트 좌표 기준 `VENT`가 `LED`와 거리 45 미만 | 주의 |
| IP 등급-시장 습도 부적합 | 목표 시장이 고온다습권(아시아·동남아·중동·중국)인데 등급 <66 | 높음 |
| IP 등급 통과지만 이력 대조 요 | 위와 같되 등급 ≥66(스펙은 통과, 이력 대조 권장) | 주의 |
| 밀폐 하우징 벤트 부족 | 하우징이 "밀폐" 계열인데 벤트 ≤1개소 | 높음 |

## 데이터 흐름
1. `POST /api/drawing-input` — DXF 업로드(최대 10MB, `.dxf`만) 또는 `{"sample": true}`로 서버가
   즉석 생성한 샘플 도면. `parseDrawing(parseDxfEntities(...))`로 파싱 후 기존 인제스천 파이프라인
   (`ingestOne` → `mergeDelta`)으로 온톨로지에 합류(스키마 없음 409, 동일 파일명 409 — `/api/ingest`와
   동일한 두 가드). 형상 특징을 가진 `proj` 노드를 `setActiveDrawing`으로 지정(이후 자연어 질의의
   "이 도면/이 커넥터" 지시 대상). `analyzeDrawing` + `assessDrawing`을 호출해 유사 설계·취약점·조건
   후보를 응답에 담는다.
2. `GET /api/drawing-svg?file=<도면.dxf>` — 현재 캔버스에 등록된 DXF를 SVG로 렌더해 미리보기 반환.
   파일명은 경로 구분자 없는 `.dxf`만 허용(디렉터리 탈출 방지), 이 캔버스에 없으면 404.
3. `GET /api/design-options` — `proj` 노드 props 에서 시장·광원·형상 값을 **distinct 로 추출**(하드코딩
   목록 아님). 형상 값은 IP 등급·소재·개수·서술문 같은 잡음을 정규식(`SHAPE_NOISE`)으로 걸러낸다.
4. `components/DrawingPanel.tsx`가 제목블록·형상 특징·취약점 카드·유사 설계 카드(유사도%·일치/불일치
   칩·발생 이력·차종)를 렌더링하고, "이 조건으로 추론 실행" 버튼으로 조건 후보를 `POST /api/infer`에
   넘긴다.

## 골든 룰 · 확장 이음새
결정론적·설명 가능이 원칙 — 벡터 임베딩 없이 특징별 가중 규칙으로만 점수를 내고, 모든 판정에
`matched`/`differed` 근거 문구를 동반한다. 확장 시에는 `shapeSimilarity()` 내부를 지오메트리
임베딩 코사인 유사도(예: Milvus)로 교체하되 **시그니처는 유지**하는 것이 설계된 확장 지점이다.

설계 결정 기록: [2026-07-06-2d-drawing-design.md](../../superpowers/specs/2026-07-06-2d-drawing-design.md)

## 왜 레거시인가
형상 특징 모델(`ShapeFeatures`) 자체가 램프 도면의 벤트·실링·개스킷·하우징 어휘에 종속돼 있어
다른 부품군 캔버스로 옮기려면 특징 스키마부터 다시 정의해야 한다. `GET /api/design-options`도
`proj` 노드 props 에서 시장·광원·형상을 뽑는 FMEA 설계조건(`DesignInput`) 전용 드롭다운이다.

다만 이 세 라우트(`drawing-input`·`drawing-svg`·`design-options`)는 `lib/capabilities.ts`의
`Capability` 목록에 없어 `infer`·`fmeaDraft`·`contradictions`·`bomCheck`처럼 `requireCapability`로
409 차단되지는 않는다 — FMEA 객체타입이 없는 캔버스에서 호출해도 서버가 막지는 않고, 다만 `proj`
형상 데이터가 없으니 유사 설계·조건 후보가 비어서 나올 뿐이다.
