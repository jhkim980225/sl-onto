# feature: 검토의견 RAG · 추론 오케스트레이터

> **레거시 — FMEA 전용.** 이 기능은 동작하지만 신규 투자 대상이 아니다.
> 추론 결과(`DesignInput`·`InferResponse`·`MasterAudit`)에 종속돼 `default`(램프) 캔버스 밖에서는 의미가 없다.
> **두 모듈 다 게이트가 걸려 있다.** orchestrator 는 `POST /api/infer` 를 경유해
> `requireCapability("infer")`(`fm`·`cause`·`item`)를 물려받는다. review-opinion 은
> **`reviewOpinion` 케이퍼빌리티**로 직접 막힌다 — `infer` 와 `contradictions` 를 둘 다 호출하므로
> 요구 타입은 두 기능의 합집합(`fm`·`cause`·`item`·`reg`)이다.
> 제품의 현재 방향은 [../../README.md](../../README.md) 참조.

## 책임
이 문서는 서로 다른 일을 하는 **두 개의 독립 모듈**을 함께 다룬다 — 한 서브시스템이 아니다.

- **`lib/review-opinion.ts`**(60줄) — AI 종합 소견 RAG. 체크리스트를 사내 LLM에 넘길 컨텍스트로
  요약·조립하고, 조건을 캐시 키로 정규화·해시한다. 판정 로직은 없다.
- **`lib/orchestrator.ts`**(79줄) — 추론 파이프라인 v0. 기존 [`infer()`](그래프-추론.md)와
  [`checkBom()`](BOM-정합성.md)을 순서대로 호출하며 단계별 실측 요약(counts·ms)을 기록한다.
  **새 판정 로직은 0개** — 기존 함수를 감싸는 오케스트레이션 계층일 뿐이다.

## `lib/review-opinion.ts` — AI 종합 소견 RAG
- `canonicalCondition(input)`: `DesignInput`을 고정 키 순서 JSON 문자열로 정규화(캐시 키·해시 입력의
  결정성 보장).
- `hashKey(input)`: `lib/fold.ts`의 FNV-1a 32bit 해시(hex) — 결정론적 캐시 키.
- `describeCondition(input)`: 사람이 읽는 조건 요약(`Checklist.tsx` 헤더와 동일 톤 — 부품 앵커
  모드 vs 신규 설계 조건 모드).
- `buildReviewContext(infer, contradictions)`: `infer()` 결과(체크리스트 상위 8·`masterAudit`
  커버리지 요약)와 전역 모순 스캔 결과(제목 상위 5)만 모아 `ReviewContext`를 만든다. **컨텍스트는
  `InferResponse`·`MasterAudit`·`Contradiction`에서만 오고, 임의로 지어내지 않는다** — 근거 우선
  골든 룰이 여기서도 유지된다.

이 컨텍스트는 `app/api/review-opinion/route.ts`(`POST /api/review-opinion`, `maxDuration=180`)가
소비한다: 캐시 키로 DB(`ai_opinions` 테이블, `dbEnabled()`일 때만)를 먼저 조회하고, 없으면
`infer(condition)` → `buildReviewContext` → `llmReview()`(사내 LLM, 체크리스트 `CHECK n` 인용
포함)를 호출해 소견을 생성·캐시한다. LLM 응답이 지연되면 503.

UI: `components/Checklist.tsx`의 "🤖 AI 종합 소견" 버튼(`fetchOpinion`)이 이 API를 호출하고,
응답 본문 중 `CHECK n` 언급을 클릭 가능한 링크로 렌더링해 해당 체크리스트 항목으로 스크롤한다.
소견 카드 하단에 "LLM 생성 초안 — 최종 판단은 엔지니어"와 생성 시각·캐시 여부를 표시한다.

## `lib/orchestrator.ts` — 추론 파이프라인 v0
`runPipeline(input)`은 4단계를 순서대로 실행하며 `PipelineStep{name, ms, summary, counts}`를 쌓는다.

| 단계 | 내용 | ms 측정 |
|---|---|---|
| 조건분석 | 입력 정규화 + 모드 판정(부품 앵커 vs 신규 설계 조건) | 0(별도 측정 안 함, 정직하게 0 표기) |
| 그래프 탐색·체크리스트 | `infer(input)` 그대로 호출 — 핵심 단계 | 실측(`Date.now()` 전후 차) |
| 마스터 대조 | `infer()` 결과 안의 `masterAudit` 요약만 표기(연산은 `infer()` 내부에서 이미 끝남) | 0 |
| BOM 정합성 | `anchorItem`이 있을 때만 해당 부품에 `checkBom()` 호출 | 실측 |

반환값 `PipelineResult`는 `InferResponse`에 `pipeline: PipelineStep[]`을 얹은 것뿐 — 체크리스트
자체는 `infer()`와 동일하다. `orchestrator.ts`에는 자체 라우트가 없다: `app/api/infer/route.ts`가
`infer(input)` 대신 `runPipeline(input)`을 호출해 `POST /api/infer` 응답에 `pipeline` 필드를 얹는
방식으로 오케스트레이터를 경유시킨다. 따라서 `orchestrator`는 `infer`의 `requireCapability("infer")`
409 게이트를 그대로 물려받는다.

UI: `Checklist.tsx`의 `pipe-strip`이 `pipeline` 배열을 단계별 칩(`이름 · ms · ✓`)으로 표시한다.

## 골든 룰
`orchestrator.ts` 코드 주석 그대로: **"연출용 숫자 금지 — counts 는 전부 실측."** ms 를 측정할 수
없는 파생 단계(조건분석·마스터 대조)는 그럴듯한 숫자를 지어내는 대신 정직하게 `0`으로 표기한다.
각 단계는 "확장 시 LLM/외부 에이전트로 갈아끼워지는 슬롯"으로 설계되어 있다 — 지금은 그 슬롯에
기존 규칙 기반 함수가 그대로 꽂혀 있을 뿐이다.

## 왜 레거시인가
두 모듈 다 FMEA 전용 타입에 직접 의존한다 — `review-opinion`은 `DesignInput`·`InferResponse`·
`MasterAudit`·`Contradiction`을, `orchestrator`는 `infer()`·`checkBom()`과 그 입출력 타입을 그대로
가져다 쓴다. 다만 실제 409 차단 방식은 두 모듈이 다르다: `orchestrator`는 `/api/infer` 라우트를
경유하므로 그 라우트의 `requireCapability("infer")` 게이트를 물려받아 FMEA 타입 없는 캔버스에서
막히지만, `app/api/review-opinion/route.ts`는 `requireCapability`를 호출하지 않는다 —
`lib/capabilities.ts`의 `Capability` 목록에도 `"reviewOpinion"`은 없다. 즉 다른 캔버스에서
`POST /api/review-opinion`을 호출해도 서버가 409로 막지는 않고, `infer()`가 내부에서 빈 결과를
반환할 뿐이다.
