# DB 직독(리드 경로) 전환 1단계 — 요청별 Postgres 동기화

- 날짜: 2026-07-09 · 배경: "인메모리 캐시로 조회하지 말고 실제 DB 물려서" (사용자 지시)
- 현 구조: DB=원본(쓰기 write-through)이지만 조회는 부팅 시 1회 하이드레이션한 인메모리 인덱스.
  파드 생존 중 DB 직접 변경(psql·타 레플리카)은 재시작 전까지 안 보임 — "실제 DB 사용" 체감 깨짐.

## 결정

**모든 API 요청은 응답 전에 Postgres에서 그래프를 재동기화한다** (`ready()`가 매 호출 `loadAll()` 재적재).

- 도메인 로직(search/infer/quality/…)의 sync 접근자 시그니처는 유지 — 인덱스는 "요청 시점 DB 스냅샷"이 된다.
- 동시 요청은 진행 중 동기화 프로미스를 공유(중복 SELECT 방지).
- 현 규모(≈180 노드/2.2k 엣지) 재적재 = 수 ms. 수만 노드 도달 시 2단계(대상 지정 SQL·recursive CTE)로 이관
  — 그때도 라우트는 불변, store 내부만 교체.
- `DATABASE_URL` 없는 환경(단위 테스트·로컬)은 기존 인메모리 경로 유지(테스트 인프라 비용 회피).
  프로덕션은 항상 DB 모드.
- 검증 기준(핵심): **psql로 DB에 직접 INSERT한 노드가 파드 재시작 없이 다음 API 응답에 나타난다.**

## 2단계(후속, 실데이터 스케일 시)

- 조회를 전면 재적재에서 대상 지정 SQL로: 검색 후보 = ILIKE+pgvector, 상세 = JOIN, 탐색 = recursive CTE
- 인메모리 인덱스 제거, replicas>1 해제
