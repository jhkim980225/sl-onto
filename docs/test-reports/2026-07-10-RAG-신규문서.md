# 테스트 리포트 ② — 신규 문서 추가 → RAG 반영 검증

- 일시: 2026-07-10 · 대상: v54 프로덕션 · 흐름: **신규 xlsx 업로드 → 온톨로지 병합(Postgres) → 임베딩 백필 → LLM RAG 질의**
- 방법: 기존 온톨로지에 전혀 없는 고유 내용으로 FMEA xlsx를 합성 생성해 `POST /api/ingest` 업로드, 단계별 반영을 API로 검증.

부품 "레이저 스캐너 모듈 LSM-g32s" · 고장모드 "미러 코팅 박리" · 원인 "고온다습 환경 코팅 열화" · 조치 "코팅 공정 사양 강화(2회 도포)" · 발생프로젝트 PJ 2026-HL21 (전부 기존 온톨로지에 없는 신규 어휘)

## 판정: PASS

새로 추가한 문서의 내용이 ①온톨로지(Postgres) ②임베딩 색인 ③LLM RAG 답변까지 **전 구간 자동 반영**됨을 확인. 답변 인용([R n])은 전부 신규 생성 관계였고, 없는 정보는 지어내지 않음.

## 관찰·한계

- **원인·조치는 fm 노드에 질의해야 나옴** — 온톨로지 구조상 CAUSED_BY/MITIGATED_BY가 고장모드에 걸리기 때문. 부품 질의에서 2-hop(부품→fm→원인)까지 컨텍스트에 넣는 확장 여지 있음(현재 1-hop).
- **자연어 검색(nlsearch)은 신규 어휘 0건** — 규칙 스코어러가 후보를 보수적으로 거르는 설계라, 사전에 없는 새 개념("미러 코팅 박리")은 규칙 점수를 못 받아 탈락. 키워드 검색(`/api/search`)과 객체 질의는 정상. nlsearch의 임베딩-only 후보 허용(낮은 점수)이 후속 개선 후보.
- 테스트 데이터는 검증 후 큐레이션 API로 전량 삭제(온톨로지 원복 — 잔존 0). 재현: 위 스키마(부품/고장모드/원인/현행조치 컬럼)의 xlsx를 UI 문서 인제스천 또는 `POST /api/ingest`로 업로드.
